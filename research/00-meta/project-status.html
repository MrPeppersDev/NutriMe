1What NutriMe is

A personal nutrition and meal-planning system whose purpose is to remove food-related cognitive load. Hand it a health profile and taste preferences once, get continuously-updated answers to what am I eating today, when do I cook it, how does it get to my kitchen.

Local-first, single-device macOS. HIPAA-discipline posture even though not legally required. Personal-use primary, with active open-source publication ambition — four publication targets are in flight (GLIM screener; hybrid LLM + CAT + structured-instrument intake agent; OSS nutrition intake chatbot; recipe time-feedback aggregate data).

Market gap: cooking whole foods + wearables-driven personalization + multi-user household balancing + grocery delivery integration + explanation-driven recommendations + cooking-time-aware planning. No existing product combines all six. PlateJoy — the closest competitor — shut down in 2025.

Canonical scope document: product-framing.md. Non-negotiable safety rules: constitutional-rules.md.

2Methodology

The project is being run as a deliberate, research-first program. No application code through Stage 3.5. Decisions are taken topic-by-topic: a proposal with tradeoffs, the user calls it, the resolution is captured in the appropriate 00-meta/*.md doc, and it gets committed with a structured message (e.g. schema(S12): migration strategy + closes Stage 3.5).

Each open question moves through the document lifecycle: surfaced (in a sweep or upstream block) → flagged in roadmap.md → resolved in synthesis.md / architecture.md / schema.md → committed. When a cross-cutting principle emerges (e.g. phi-handling.md, provider-abstraction.md, preservation-layer.md) it gets promoted to its own meta doc.

User direction on planning depth

"We're looking at just building what we need and ensuring that it works in the ways that we need it to." No 5-year strategic plan. But every decision is taken deliberately with the research substrate behind it.

F5 — generic inference catch-all type   [issue #3]

What. Of 16 synthesized entry types, 15 are specific shapes (nutrient_intake_estimate, meal_recommendation, dietary_constraint, etc.). The 16th, inference, is a deliberately generic catch-all for cases that don't fit any specific bucket.

Why it's flagged. Generic catch-all types are usually a schema-design smell. Kept anyway at ~65% confidence because forcing every inference into a specific type today would mean inventing speculative types.

Build-time work. Monitor where inference entries cluster. If a recognizable subtype emerges (e.g. wearable↔food correlations), promote it to a specific synthesized type and shrink the catch-all. Goal: drive inference use toward zero over time.

Molecule-level weakest-tier heuristic for evidence_tier   [rolled into issue #4 — (ζ) substrate revisits]

What. When a molecule (composite atom group) needs a displayed evidence_tier, the rule is: take the weakest tier among constituent atoms.

Why it's flagged. Honest but potentially misleadingly pessimistic. A meal recommendation built from Strong-evidence nutrition + Suggestive operational-tradition flavor pairing displays as "Suggestive" — undersells the nutrition piece.

Build-time work. Watch query patterns. May prefer per-atom joins to a pre-rolled-up tier.

(ζ) Collapse embeddings table + vec0 into single virtual table — S5 Q5.3   [issue #4]

What. Embeddings currently live in two parallel tables (normal SQLite for metadata; vec0 virtual table for vector search). sqlite-vec may support a single virtual table with auxiliary metadata columns.

Build-time work. Verify hands-on: do CHECK constraints, partial indexes, and S11 FK semantics work cleanly on the virtual table? If yes, swap. If no, current main-table-plus-vec0 design stands. Application surface (the Q5.5 resolver) doesn't change either way.

(ζ) subject_registry alternative for loose polymorphic refs — S11 Q11.2   [issue #4 — bundled with the other ζ revisit]

What. Polymorphic foreign keys (a column pointing to atom OR molecule OR synthesized entry) can't be enforced by normal SQL FKs. Current plan: enforce in application code + orphan_sweep_polymorphic_refs job.

Alternative. Single subject_registry table mapping (id, type) → existence; FK to that registry. Cleaner if it works.

Build-time work. Validate at build alongside the broader (ζ) collapse. If FK semantics work for both virtual and regular tables, swap to FK-native enforcement.

S10 build-time tuning concerns (three knobs)   [issue #5]

What. S10 deterministically maps raw quality factors → system_aggregate_quality_score → user-facing certainty (Strong / Moderate / Suggestive). Three knobs need empirical calibration on real data:

  1. Weight values — how much does each factor (evidence_tier, verification_status, source authority, derivation depth) contribute?
  2. Verification-failed multiplier — when a verification step fails, how much does the score drop?
  3. Deep-chain compounding — how does confidence degrade as inferences derive from inferences? Multiplicative? Logarithmic? Capped?

Build-time work. Can't be tuned in the abstract. Calibrate against real data once the system is producing entries.
