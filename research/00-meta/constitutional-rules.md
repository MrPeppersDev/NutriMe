# NutriMe — Constitutional Rules

> Non-negotiable, project-wide rules. These bind every sweep, every feature, every surface.

## Rule 1 — Consult a professional

**Anywhere the system surfaces conflicting, uncertain, weak-evidence, or borderline-clinical guidance, it must explicitly direct the user to consult a doctor or licensed nutritionist.**

This applies to:

- Conflicting authoritative bodies (US NASEM vs. EFSA vs. WHO disagree)
- Tier 3 / Tier 4 evidence (see [evidence-tiers.md](evidence-tiers.md))
- Clinical-adjacent topics (diabetes management, kidney function, eating disorders, pregnancy, etc.)
- Supplements
- Drug-nutrient interactions
- Any user-disclosed clinical condition, regardless of the strength of the underlying evidence

The disclaimer must be **adjacent to the uncertain content**, not buried in a footer. The product never withholds information by default — the rule is *transparency plus appropriate redirection*, not gatekeeping.

## Rule 2 — Evidence transparency over evidence gating

NutriMe surfaces weak evidence rather than hiding it, but always with a clear declaration of evidence quality. See [evidence-tiers.md](evidence-tiers.md). The product never claims certainty it does not have.

## Rule 3 — No food / macro / calorie logging

NutriMe does not implement user-initiated food / macro / calorie tracking. Personalization derives from intake, optional wearable signals, and passive confirmation + semantic feedback. See [product-framing.md](product-framing.md) and [intake-pattern.md](intake-pattern.md).

**Important distinction — inventory tracking is NOT in this prohibition.** Knowing what's on hand in pantry/fridge/freezer (so the system can use existing ingredients, avoid reordering, and reduce waste) is a distinct data layer in scope per [intake-pattern.md inventory awareness layer](intake-pattern.md#inventory-awareness--a-parallel-data-layer). The line:

- *Logging (out)*: tracking what you ate; computing calories/macros consumed; backward-looking food accounting
- *Inventory (in)*: knowing what's on hand to use; forward-looking utility for meal planning + shopping list construction

The user never opens a "what did I eat today" form. The user does, however, tell the system (or the system observes) what's in the kitchen so it can plan around what's there.

## Rule 4 — No recipe generation

Recipes are sourced from existing curated collections, peer-reviewed APIs, open datasets, and public-domain cookbook corpora — never generated by the LLM. See [recipe sourcing scope (sweep #11)](../11-recipe-sourcing/scope.md) when scoped.

## Rule 5 — International by default, geographically respectful

NutriMe defaults to the user's home country (or current country if living abroad, with home country given priority). It always surfaces alternative dietary patterns and cultural frameworks so the user understands their home country is one option among many. See [sweep #1 scope](../01-international-nutrition-standards/scope.md).

## Rule 6 — Health data stays local where possible

Wearable, biometric, and health data should be processed locally; only computed targets / derived signals should be sent to cloud LLMs. (Architectural rule, will be revisited when tech is on the table.)

## Rule 7 — Peer-reviewed evidence floor

Every system design decision (defaults, gating logic, recommendation algorithms) and every user-facing recommendation surface must be grounded in **peer-reviewed evidence (Tier 1, 2, or 3)**. Tier 4 (mechanistic-only, vendor whitepapers, preprints, conference abstracts, blog posts) cannot serve as the sole basis for any health claim.

Tier 4 *may* appear as informational / cultural / historical context where no health claim is attached (e.g., "this dietary pattern is traditional in X region" is a cultural fact; "...and improves cardiovascular outcomes" requires peer-reviewed support).

See [evidence-tiers.md](evidence-tiers.md) for tier definitions and surfacing rules.

## Rule 10 — User decides with full context

When NutriMe encounters a conflict between a user request and the system's knowledge (clinical contraindications, allergens, life-stage cautions, evidence-weak choices, etc.), the system **surfaces the conflict, provides full context, and lets the user decide.** It does not refuse outright. It does not silently modify. It trusts adult users to make informed decisions about their own lives.

A critical nuance: **recipes / meals are not always for the requesting user.** The user may be cooking for a household member, a guest, a friend who eats differently. When a request touches a contraindication on file, the system asks "for whom" and applies gating to the eater, not always the requester.

The framework:

1. **Detect** the conflict
2. **Surface** it explicitly in plain language
3. **Provide full context** — relevant evidence per [evidence-tiers.md](evidence-tiers.md), relevant constitutional considerations (consult-professional, audit-as-education), relevant alternatives
4. **Defer** the decision to the user
5. **Honor** the user's decision and preserve the trail per [epistemic-trail.md](epistemic-trail.md)

This rule is meta over Rules 1, 7, 8, 9: those govern what guidance the system itself produces; Rule 10 governs how disagreement between system guidance and user choice is resolved — by transparency + user agency.

See [user-decision-framework.md](user-decision-framework.md) for operational details.

## Rule 9 — Geographic neutrality in evidence surfacing

The user's geographic location is a **logistics / utility data point, not a content filter**. All valid, peer-reviewed, well-sourced recommendations are equal-weighted in what the system surfaces to the user, regardless of which country's authority published them.

The system surfaces the full global menu of authoritative evidence (USDA, CDC, EFSA, NHS, NHMRC, Health Canada, WHO, regional equivalents) without defaulting to or prioritizing the user's home-country body. The user makes an informed decision across the menu rather than seeing only their home authority's position.

**Geography IS used for** (utility / logistics):

- Grocery delivery logistics
- Local ingredient availability
- Local provider / lab / specialist directories (when applicable)
- Time zone / cooking-time scheduling
- Regulatory environment for app distribution (developer concern, not user-content concern)

**Geography is NOT used for** (content filtering):

- Filtering which authoritative bodies' guidance appears
- Defaulting which body's recommendation receives prominence
- Weighting the credibility of any peer-reviewed source

This rule strengthens [evidence-tiers.md](evidence-tiers.md): all Tier 1 sources are equal regardless of country of origin; the system never down-weights or omits a body for being "not local."

This rule has a downstream design challenge: presenting a multi-source global menu without overwhelming the user. Patterns under research in [sweep #8](../08-nutrition-education-delivery/scope.md): synthesis-with-expansion ("most authoritative bodies recommend X–Y; see all sources"), progressive disclosure based on engagement signals, comparative tables for users who want depth.

## Rule 8 — Epistemic trail of honesty

When NutriMe correlates, infers, combines, or interprets data to surface conclusions or recommendations to the user, the system must:

1. **Track provenance** — every input retains a documented source
2. **Document cross-referencing logic** — show the reasoning chain that combined sources, including assumptions
3. **Verify before presenting** — verification pipelines validate inferences before they reach the user
4. **Surface the trail to the user** — provenance + reasoning + verification status are first-class user-visible content, not hidden
5. **Be explicit about AI limitations** — acknowledge that AI correlation is not always perfect, that combinations of sources can produce errors individual sources do not, and that the user should bring uncertainties to a clinician

This is the AI-correlation-specific complement to Rule 1 (consult-professional) and Rule 7 (peer-reviewed floor): Rule 1 says "if uncertain, refer out," Rule 7 says "system behavior must be peer-reviewed grounded," Rule 8 says "when the system *does* correlate to draw a conclusion, show your work."

See [epistemic-trail.md](epistemic-trail.md) for the operational definition.
